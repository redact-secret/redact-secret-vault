# Bulk restore authority, vault-interop-v1

Status: accepted Vault interoperability boundary for #168, implemented reference adapter for the JavaScript in-memory and persistent servers (persistent two-stage path tested with the non-durable memory store). This specifies a language-neutral contract; it does not claim that a network service or Python adapter ships. Shared capture revision: `vault-interop-v1`.

## Operations and trust

A restore plan is an ordered list of occurrences, each with the exact issued token and destination path. Repeated tokens are separate occurrences. The application supplies authenticated context, authoritative capture sources, sink, purpose, tenant/session context, and the authority instance. The model must not supply those permissions. The authority owns token lookup and all lifecycle and authorization checks; the engine owns parsing, output sizing, and reconstruction. Neither component exposes an arbitrary mapping iterator.

`preflight(plan) -> opaque grant` validates the whole request and releases no values, consumes no uses, and reserves nothing. The grant binds authority instance, trusted request snapshot, and exact ordered plan. It is single-use and not a bearer permission. `consume(grant, plan) -> resolved values` revalidates all mutable eligibility and atomically consumes all requested occurrences or none. Successful handoff contains exactly one complete value per occurrence, in plan order, including duplicates. Nothing is returned before successful consumption. Reconstruction failure after success cannot refund consumption.

Each operation checks existence, source membership, authority/session binding, tenant/principal, sink/path grants, nonempty purpose, logical expiry, revocation, occurrence budget, current application policy, and request limits. Persistent namespace/session ownership is resolved by the persistent server. In-memory session isolation is the owning server instance; optional `sessionId` is supplied to application policy and is not independently stored or authenticated. Applications requiring named sessions must check them in policy or use persistent server session resolution. A grant cannot cross authority instances.

## TypeScript reference

`createRestoreAuthority(server, trustedRequestWithoutFields)` returns asynchronous `preflight` and `consume`. `RestoreAuthorityPlan.occurrences` contains `{ token, path }`. Generic trusted context is detached with `structuredClone` at preflight. Contexts that cannot be cloned require the optional trusted `snapshotContext` callback, which must return a stable detached or immutable request context. Snapshot failure denies before authority interaction with a bounded error. Fresh principal resolution and external policy still run at consume. The adapter accepts canonical 32-byte ASCII `<rsv_` + 26 lowercase base32 characters + `>` tokens, at most 4,096 occurrences, and path strings of 1–128 characters. Server identifier validation and configured field/count/byte limits additionally apply. Occurrence lists and token/path entries must be own data properties; accessor plans are rejected without invocation. The adapter rechecks plan correspondence after asynchronous consume, returning only a committed failure if the caller changed the plan during that operation. The adapter groups tokens under their original paths, validates the entire group, and explicitly reorders the committed value vector into plan order. JavaScript numeric property ordering is accounted for. Values are obtained from the authority's exact requested occurrence handoff, never inferred by splitting reconstructed plaintext.

The in-memory `Vault` and `ServerVault` expose `preflightRestore(request)` and `consumeRestore(request)`. The latter returns existing restore metadata plus `values`, ordered by actual request field enumeration then textual token order. The reference adapter translates this profile-specific ordering into the portable plan ordering. Ordinary `restore` results remain unchanged. Server preflight and consume each run on its single-flight queue; the gap between them is deliberately unreserved. Consume reruns principal resolution, policy, lifecycle and budget checks. Validated own-data field snapshots are used across asynchronous callbacks.

## In-memory ordering decision

The prior implementation constructed restored fields privately **before** mutating budgets, despite a comment claiming the reverse. It then mutated every budget synchronously, removed exhausted entries, emitted a bounded audit event, and returned. This differs from the engine's observable consume-then-reconstruct sequence but not its release boundary: private construction is not delivery.

Decision: preserve private construction before the synchronous mutation, share complete validation with preflight, and hand off requested values only after mutation succeeds. This avoids consuming a request if private construction fails and preserves all-or-none consumption. No callback or asynchronous suspension exists between construction and budget mutation; policy callbacks cannot reenter the core. The server queue serializes its own capture, revoke, restore and dispose. Caller-visible reconstruction by the sibling engine happens after committed handoff and therefore has no rollback guarantee.

## Persistent mapping and compatibility

The existing persistent restore server owns context/session/policy, decrypts authenticated records privately, and submits one `commitRestore` batch with capture generations, entry lifecycle/ciphertext revisions, aggregate counts, attempt ID, and bound request digest. The store checks namespace recovery epoch, logical expiry, revocation, generation/revision freshness, and budgets at one whole-request transaction. Store checks cannot replace server authorization. Receipts retain commit knowledge, never plaintext.

The persistent server shares its existing authorization/decryption validation between preflight and consume. Preflight returns before plaintext bytes become strings or any store commit, and wipes decrypted private payload buffers in its existing finally block. Prepared grants retain only the request snapshot and occurrence correspondence, never decrypted values. Consume starts from fresh context resolution, rereads and decrypts current records, reevaluates policy, then uses the existing #105 transaction and fail-closed ambiguity rules. Do not implement preflight by calling existing `restore`, by granting directly from a store read, or by replaying receipt values. This change implements **in-memory and persistent reference compatibility**. The new persistent two-stage path is tested against the non-durable memory store; it does not add PostgreSQL deployment qualification or expand existing store/runtime support claims. Existing persistent restore behavior and qualification scope are unchanged. Policy executes outside the transaction: the existing policy revision fence narrows its residual race window but does not atomically commit independent identity/policy services with storage.

## Failure and commit knowledge

| Outcome | State | Values and retry |
| --- | --- | --- |
| Invalid request/grant, current authorization or lifecycle denial before commit | `not-committed` | None; fix the cause, do not widen permission |
| Successful batch; later output validation/reconstruction fails | `committed` | No automatic rollback or replay |
| Commit transmission/acknowledgment cannot establish outcome | `indeterminate` | None; resolve the bound attempt, never blindly retry |
| Receipt confirms prior successful attempt | `committed` | No plaintext replay |

The reference error exposes only fixed text and commit state. Unknown server failures conservatively become `indeterminate`; known precommit `RESTORE_DENIED`, `INVALID_ARGUMENT`, `DISPOSED`, and `BUSY` become `not-committed`. Definitive `STORE_UNAVAILABLE`, `STORE_QUARANTINED`, `CLOCK_SKEW`, and exhausted stale-retry `RESTORE_CONFLICT` outcomes are also `not-committed` under the existing store contract. `attempt-already-committed` is `committed`, not a fresh successful release. A malformed success vector is a `committed` adapter error. Never propagate callback messages, raw input, tokens, values, or maps through errors/logs. Persistent `COMMIT_AMBIGUOUS` maps to `indeterminate` and carries only its opaque `attemptId` for reconciliation; `resolveAttempt` may establish committed or definitive not-committed under its existing recovery/receipt rules. A missing receipt alone is not proof after its retention horizon.

## Sibling compatibility

Compared against `redact-secret/restore` commit `e9c4863bf887956d004438d0229d04a9a85667dc`, `src/authority.rs` and `docs/authority-semantics.md`, for restore#5/#8. Its `RestoreAuthority` trait is synchronous and bulk, with opaque grant and ordered `ResolvedValues`. Its requirements for fresh eligibility, duplicate use counts, truthful commit states and no plaintext replay agree with this boundary. JavaScript's asynchronous adapter requires an explicit trusted bridge; it does not turn the Rust synchronous trait into a network or cancellation protocol. Do not claim remote cancellation or distributed delivery atomicity. The engine must reject a wrong-length handoff and enforce output bounds after committed consume.

Evidence: `packages/vault-server/test/interop-restore.test.mjs` checks nonconsuming preflight, exact plan ordering including numeric paths and duplicate tokens, revoke/expiry/policy/budget changes between stages, unrelated-budget preservation, grant isolation/reuse, and mutation rejection. `packages/vault-server/test/persistent/interop-restore.test.mjs` checks nonconsuming persistent preflight, ordered duplicate handoff, whole-batch consumption, revalidation and audit leak hygiene. Cross-repository roundtrip evidence belongs to the interoperability qualification record.
